# native文字抽出と文字番号による照合

nativeのファイル変換は、SDKのページ全文と、矩形ごとに抽出した本文の非空白文字の順序・件数を照合する。
添字や下げた文字などで矩形が重なると、異なる矩形から同じ文字が返る場合がある。
不一致を検出した場合は既存の文字番号による抽出を試し、全文と一致する場合だけ採用する。
文字列の部分一致や反復の見た目から文字を消す処理ではない。
所有PDFの `AAA` など、本物の反復は保持する。

文字番号経路を採用した後も、pure/nativeのページ単位の照合、生成fontのcmapとの照合、
Formの抽出順の検証は維持する。Unicodeを推測して一致条件を緩める処理は加えていない。
API・CLI・設定・依存の追加はない。文字番号による回復自体はnativeが対象で、bytes/WASMの文字抽出規則は変更しない。
同じ水平text objectの連続文字は、元の矩形抽出と本文・font・色・基線・object外接矩形が
完全に一致する場合だけ、元の幾何を持つspanへ戻す。一致しない箇所は文字単位を維持する。
SDKの公開object幾何を使い、private handleや文字ごとの全ページ再走査は使わない。
共通DOCXの下線判定は変更しない。

## 制御文字と予算

SDKは実際に描画した字形を制御コードへ対応させることもある。
SDKが生成した改行と、元から描画されたC0/C1制御コードを区別し、後者があるページでは回復を採用しない。
SDKのhyphen判定で別途確認した印刷ハイフンは例外とする。
たとえばGNUの未確認 `circlecopyrt` を改行として消したり、別のUnicodeへ割り当てたりしない。
この字形を含む既知の2ページは従来の本文・幾何・font選択を保持し、Encoding診断とstrictの拒否を維持する。

照合中も停止済み予算を検査する。追加抽出の索引・文字列・要素は既存の累積metadata予算へ算入し、
容量不足を無視して途中の結果だけを返さない。不可視文字・部分clipの既存経路と拒否も維持する。

## 実資料の検証と限界

[検証台帳](../corpus/validation-native-segment-identity.json)に原本・コミット・測定範囲を記録している。
原本とgoldは既存の事前確認済みのものを使い、PDFやfontをGitへ追加していない。

GNU Helloでは原本10ページ目の `LaTEX` 付近が `LaTETEXEX` となり、ページ全体がnativeの代替処理へ回っていた。
修正後のこのページはpureの本文・座標・font選択と一致し、原本17ページに対するnative出力も18から17ページへ戻った。
残る16ページは解析結果が同一で、余分な出力ページを除いた対応関係で描画画像も同一だった。
ページ数の一致だけで文書全体を合格にはしていない。

EfficientNetとBERTの変更した原本9ページでは、独立した同じSDKの検査で、
修正前が矩形の反復抽出、修正後が各文字番号を一度ずつ読んだ結果と一致した。
添字 `TiTi` / `TjTj` や引用文献の `ECCV,V,` などの重複が解消した。
変更した原本ページごとに、出力ページ群の文字別件数の差分が、独立SDK検査で確認した
重複の差分（EfficientNet計42字、BERT計24字）と一致した。
これは読み順・数式の組版・字形や配置全体の合格を意味しない。
BERTの既存Table1 goldの45セルは、DOCX本文内で各行の数値が連続し、5行の順番も維持した。
EfficientNetのTable1がある原本5ページ目は、修正前後でnativeの解析結果が同一である。
これは表の編集可能な格子・字形・配置まで正しいという判定ではない。

EfficientNetは原本10に対して19ページ、BERTは原本16に対して27ページのままである。
数式の構造、回転した軸ラベル、vector図、表の行列関係、未確認Unicodeは引き続き課題である。
Microsoft Wordや未見のholdoutを含む本番品質の認定でもない。

SDKの文字番号の意味は[PDFiumの公開text API](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_text.h)、
矩形抽出の呼出しは使用中のpdfium-renderの実装で照合した。
外部実装を転用せず、既存の抽出経路と有界な照合処理を使用している。
