# 表セルの行高を累積座標で丸める

原本の複数行がセル内に収まるかを調べる際、各行高を個別にtwipへ丸めると、丸め誤差が
行数分だけ増える。例えば、先頭の空白3.45ptと23行の7.98ptは186.99ptであり、187ptの
セル内に収まる。各行を160twipへ丸めると合計3749twipとなり、セル高3740twipを超えて
一段落のfallbackへ戻っていた。

行の開始・終了位置をptで累積し、各端点を一度だけtwipへ丸める。隣り合う端点の差を
段落前の空白と明示行高へ渡すため、上の例は3740twipとなり、23段落を保持する。
非有限値、負の空白、非正の行高、整数範囲外の値は受け入れず、失敗時に累積状態を進めない。
公開API・CLI・依存は変更しない。

元から使っている「文字のem高と非負の行間」を累積するモデルは維持する。
原本の基線間隔がem高より狭い行を正確に重ねる処理ではない。文字幅、書体の置換、
上下の基線位置、単一行セルの縦中央配置も別の課題である。

## 検証

所有PDFの公開回帰テストでは、7.98ptの23行が一段落になるRedを先に保存した。
整数のミリポイントを独立の期待値として、行数・行高を変えた24ケースの公開PBTと、
累積器の32ケースのPBTで端点誤差と範囲外入力を確認する。
別途生成した3件の所有PDFでは、文字列の順序、文字サイズ、下線なし、端点誤差1twip以内を
事前の期待値と照合した。nativeのdefault/strictとChromium/WebKitの両経路で一致する。
descenderを持つ文字も描画して確認する。

既存の国税庁印紙税額一覧では、問題のセルが一段落から原本の23行に対応する段落へ戻る。
空白以外の文字の多重集合を保ち、段落の明示行高の合計は3740twipとなる。
これは独立した全文正解や原本どおりの基線・ページ表示の合格を意味しない。
nativeの既存26結果とブラウザ100結果について、成功・拒否・変更したXMLの範囲を照合した。
EfficientNetでは行間の1twip以内の変化も確認し、変更した描画ページをすべて目視した。
論文全体の数式・図・改ページは未合格のままである。

## 新しく確認した表の未解決例

国税庁の[令和8年分・賞与に対する源泉徴収税額の算出率の表](https://www.nta.go.jp/publication/pamph/gensen/zeigakuhyo2026/data/15-16.pdf)
の原本2ページを収集した。利用条件、個人情報の有無、原本の全ページを先に確認し、
見える範囲の30論理セル・見出しを手で記録してから固定済みの変更前後の変換器を実行した。
[事前の正解記録](../corpus/nta-bonus-rate-2026-prospective-gold.json)は変更しない。

変更前後とも主な列が通常段落へ崩れ、編集可能な表は右端の一部だけになった。
Wordでは4ページとなり、行・列の所属を含む30セルの合格は確認できないため、文書全体を不合格とする。
nativeの中間表現には罫線が残っており、表の推定・組立処理を次に調べる必要がある。
元PDFのstrict拒否と、bytes/WASM経路の暗号化拒否も変わらない。
この入力は初回評価後には既知の回帰用資料となり、後続修正で未見の資料と数え直さない。

原本・font・生成DOCXはprivate QAにのみ保存し、追跡対象PDF fixtureは従来の3件を維持する。
Microsoft Wordでの表示やプロダクション品質は未確認である。
