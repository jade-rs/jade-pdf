# nativeの語間とsource variation sequence

登録済みAdobe-Japan1 CIDを正しく復号すると、国立天文台の既知暦要項でpure/nativeのページ内文字数が一致するようになった。その結果、従来の照合がpureの空白配置を採用し、以前のnativeで`1 12`だった月日が`112`に変わった。元の非空白文字の内訳だけを照合しても、この退行は分からない。また、CID `18b5`の公式Unicode対応`芒 U+E0100`はSDK側にselectorがなく、ページごとの件数不一致で失われていた。

今回のnative照合は、ページ全体でsourceとSDKの非空白Unicode順が一致するときだけ、SDKが報告した通常空白の語間位置を記録する。同じsource spanの内部にある語間を一つ保持し、sourceが明示した空白は消さず重複もしない。改行・tab・CJKのtrackingを通常の語間へ変換しない。別spanの先頭には空白を足さず、sourceの幾何とstyleを保持する。別span間の配置や単語復元まで合格したという意味ではない。

SDKがsourceのvariation selectorを省いた場合は、selectorを除くbase scalarの件数とページ全体の順序を確認する。同じspan内でbase文字に続く単独selectorだけを対象とし、leading・連続・空白直後のselectorでは対応を成立させない。生成Type1 fontを含むページの件数不一致を、この規則で救済しない。生成fontのspanへSDK由来の空白を足すこともない。SDKが別のbase文字や順番を返したページはnativeへの既存代替処理を維持する。これはvariation glyphの描画再現や、任意のUnicode正規化を保証する規則ではない。

語間位置は二回の借用走査で必要件数を数え、確保前にmetadata予算を予約する。出力文字列も全UTF-8容量を先に数え、容量不足や停止時に部分結果を公開しない。新しい依存・公開field・設定はない。bytes/WASMの文字描画命令の結合規則は変更しない。

元の既知PDF・抜粋・全ページ描画・元の44基準・以前の412変換結果は固定したままである。追加のfollowup oracleは、既知の退行と公式CID対応を確認した後、今回の製品修正前に別領域へ固定した。元goldの2,152文字を置き換えず、selectorを含む2,153文字という追加基準と月日区切りを検証する。未見資料の精度率には数えない。

公開file APIの2回帰は修正前に両方失敗し、修正後に通過した。単体PBTの最小失敗入力は`11`と`1 1`で、seedを保存している。既存の照合・容量検査9件と追加単体7件は通過した。最初の単体テスト呼び出しにはテスト自身の変数名誤りによるコンパイル失敗があり、そのログも残しているが、Redの根拠には数えていない。

全体検証、旧132ネイティブ出力との比較、WASMの再ビルド照合、変更DOCXの全ページ描画は未完了である。この候補は未適格で、元の暦要項の表・書体・図形・読み順・ページ再現の全体合格は主張しない。
